# 01. Модель игровой механики: Chat

## Назначение

Игровой чат обеспечивает общение игроков, не прерывая основной игровой цикл. В публичном кейсе используется **гипотетический** набор функций: глобальный канал, группа, личные диалоги, текстовые сообщения, непрочитанные события и серверные игровые действия из системных карточек.

Это проектная модель, а не описание функций существующего приложения.

## Сущности

| Сущность | Ответственность | Ключевые поля (пример) |
|---|---|---|
| Player | идентификация участника | player_id, display_name |
| Session | авторизация устройства | session_id, player_id, token_expiry |
| Conversation | канал, участники, история | conversation_id, type, membership |
| Message | отдельное событие переписки | message_id, client_request_id, sender_id, timestamp, content |
| DeliveryState | состояние локальной отправки | draft, sending, accepted, failed |
| ReadCursor | позиция чтения конкретного игрока | player_id, conversation_id, last_read_id |
| GameAction | действие из сервисной карточки | action_id, subject_id, status, result_version |

Поля приведены как возможный контракт; фактическую схему необходимо согласовать с backend.

## Основные потоки

### 1. Открытие / переключение канала

1. Клиент проверяет активную сессию.
2. Запрашивает список доступных разговоров и права пользователя.
3. Загружает страницу истории выбранного канала.
4. Сопоставляет новые события и read cursor; отображает непрочитанные сообщения.
5. При переключении изолирует черновики и историю соседних каналов.

### 2. Отправка сообщения

1. Игрок вводит текст и выбирает канал.
2. Клиент применяет локальную валидацию, создаёт `client_request_id`.
3. Клиент помечает сообщение как `sending`.
4. Сервер валидирует токен, членство, контент и rate limit.
5. После принятия сервер возвращает постоянный `message_id`; клиент сопоставляет его с локальным запросом.
6. Подписанные клиенты получают событие. Повторная доставка одного `message_id` не создаёт дубль.

Важно: статус **accepted** не означает, что адресат прочитал сообщение. Понятия delivered/read не включаются без подтверждения требований.

### 3. Обрыв соединения

- До получения ответа клиент не знает, был ли запрос обработан.
- Повтор допускается с тем же ключом операции; сервер должен определить судьбу первой попытки.
- После reconnect клиент запрашивает события с последнего подтверждённого курсора.
- Конфликт локального и серверного состояния решается по специфицированному правилу.

### 4. Игровое действие из сообщения

Системная карточка может инициировать действие, меняющее игровой баланс. **Сервис сообщений не является источником истины о награде**: право на получение, повторяемость и результат подтверждает игровой backend.

## Инварианты

1. Пользователь не читает сообщения разговора, где не имеет прав.
2. Одно уникальное сообщение представлено не более одного раза в истории.
3. Один успешный `client_request_id` соответствует одному серверному сообщению, если контракт поддерживает идемпотентность.
4. Успешно подтверждённое сообщение не исчезает без предусмотренного механизма удаления/ретенции.
5. Смена аккаунта не раскрывает кеш предыдущего пользователя.
6. Одноразовая игровая операция не применяется повторно при retry/двойном нажатии.
7. Отображаемый баланс после синхронизации соответствует серверному.

## Не определено и требует решения

Точные лимиты текста, максимальное число каналов, форматы контента, ретенция, условия открытия диалогов, доступность офлайн-очереди, механика unread, правила блокировок, SLA доставки и UX статусов. До их согласования проверки соответствующих полей — проектные гипотезы.
